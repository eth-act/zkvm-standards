This document defines the criteria used by the EF Research Engineering (zkEVM project) to assess a guest program's readiness for inclusion across our tools, benchmarks, and overall consideration for EIP-8025. These guidelines represent our recommendations to All Core Devs (ACD) within our team's capacity, and should not be interpreted as authoritative protocol rules for Ethereum.

## Guest program rubric

We describe the rubric by which we evaluate guest programs' readiness:
- Must implement the EEST specs and [pass all tests](https://eth-act.github.io/eest-execution-witness-dashboard/#/group/tests-zkevm%20v0.6.2).
- The ELF must comply with the defined [standards](https://github.com/eth-act/zkevm-standards/tree/main/standards).
- The ELF and Verification Key must be released as a signed asset in the guest program public repository releases, generated by a public, fully open-source CI pipeline.
- Regarding ELF generation:
  - Modified/Custom compiler: Formal verification (FV) requirements will apply to the compiled ELF (TBD by the EF FV project team).
  - No Compiler (e.g., raw assembly/manual bytecode): The raw ELF artefact will be subject to a higher degree of formal verification scrutiny (TBD by the EF FV project team).
- The repository license must be MIT + Apache 2.0.
- The team maintaining the guest program must be considered _sustainable_. While this is hard to define precisely, preference is given to guest programs maintained by established execution-layer teams or credible working groups.
- <TBD regarding benchmark requirements>

More details about some of the above points are in the following sections.

## EEST specs and tests

What the guest program should do is defined in [execution-specs](https://github.com/ethereum/execution-specs) repository under the `src/ethereum/forks/amsterdam` folder. The repository has releases with name `tests-zkevm@vA.B.C` ([example](https://github.com/ethereum/execution-specs/releases/tag/tests-zkevm%40v0.5.0)).

The releases are tags on `projects/zkevm-releases` branch, which is a merge of two things:
1. `projects/zkevm` which is the main branch where we do zkevm-related spec/tests changes, which is on top of `execution-specs` main branch (today named `forks/amsterdam`).
2. `tests-<fork>-devnet-vA.B.C` some other branch related to a devnet was launched (e.g. `tests-glamsterdam-devnet@v6.1.0`).

Refer to the latest `tests-zkevm@vA.B.C` tag to view the canonical specs and tests. If you have questions about guest program implementation or want to propose changes, open an issue in the `execution-specs` repository.

To run tests, the releases contain a `.tar.gz` with usual EEST fixtures with extra fields:
- `statelessInputBytes`: are the bytes that **must** be received in the guest program. No host manipulation of these bytes is allowed, as it can introduce new bugs/vulnerabilities not covered by EEST tests.
- `statelessOutputBytes`: are the bytes the guest program is expected to write as public input.
- `executionWitness`: for guest programs is an auxiliary field that provides more details of the execution witness encoded in the `statelessInputBytes`. Only meant for debugging reasons.

## Release ELFs in teams GH repo via CI

The ELF build for running in zkVMs should be the output of a public, fully open-source CI pipeline in your repository.

The guest program teams must publish final ELFs with proper signatures for the ELF and the Verification Keys. The zkEVM team will facilitate in [ere-guests](https://github.com/eth-act/ere-guests) some scripts/tools to do the final linking against target zkEVMs which provide libraries for [zkevm-standards](https://github.com/eth-act/zkevm-standards/tree/main/standards).

The ELF expected naming must be: `stateless-validator-<guestName>-<zkVMName>-<zkVMVersion>.elf`

In `ere-guests`, we might republish ELFs of many guest program repos verbatim, just to have a hub of all ELFs targeted for 8025. But as mentioned, no real linking, re-signing or similar will be done; the source of truth for ELFs is always the guest program teams' repository releases.
